# Shared GUI presentation: bounded diagnosis

The closed desktop-human01 was rejected for discoverability and usability. Its
reported graph appearance is narrow evidence; it supplied no workbench edit or
whole-journey acceptance. This software checkpoint neither resumes that session
nor establishes human or headset usability.

## Demonstrated presentation defects

The initial real Main/FormPanel render failed six unchanged obligations across
desktop and spatial composition: bounded opaque button/field surfaces, a distinct
actual submission action, and a rendered authored task title. The three baseline
rasters preserve those failures. The shared native Theme and FormPanel adapter
now supply the existing palette, states and authored hierarchy. Submission labels,
roles, targets, draft values and signed execution remain with their existing owners.

The candidate02 large-text render exposed clipped fields. Allowing the existing
native field scroll to receive available vertical space corrected that seam.
Candidate03 also exposed over-wide shell actions at a narrow width; the shared
native action factory measures text and constrains wrapping to its actual parent
and clipping ancestors. Neither correction shrinks text or expands hit targets.

The explicit-layout baseline05 reproduced an implementation regression: moving
every action into a footer discarded interleaved authored order. The correction
keeps native row/grid composition and column order, partitioning only contiguous
trailing actions. Tests include an actual GridContainer, not just coincidentally
vertical rectangles.

## Signed form revelation

The first signed popup enclosure assertions incorrectly treated a desktop native
popup as an embedded viewport. Main.Connect's ordinary StopSession restores native
desktop popups. The corrected test uses that actual popup's own window/content
viewport and routes software key events to its WindowId. No OS input is delivered.
The existing embedded-popup bounds remain checked in the spatial composition test.

The completed connection/setup wall displaced ordinary actions. Collapsing that
completed detail behind the existing explicit connection header retains first-run
controls and the same identity/session owners. A separate erroneous single-offer
assertion was retained: the space class really offers finite, rational and infinite
creation; the operation chooser must remain available.

Candidate10's unconditional reveal also scrolled during automatic discovery. That
failed label is retained. Reveal is now requested by an explicit subject/action
selection and fenced to its current generation; unchanged choices retain controls,
drafts and scroll position. This local presentation request grants no authority.

Candidates11/12 still left Create below the viewport. Diagnostic13 records that
the request was neither lost nor hidden: it ran while visible and scrolled 511px.
Its target was 1157px high in an 856px viewport; Create remained at y977..1025.
The actual ontology supplies layout(column) by default. The adapter's preservation
guard had excluded those column forms from the bounded field/action composition.
Candidate14 includes columns while retaining their order. The same strict native
Create check then passes at y770..818 in the actual y22..878 clipping region.

## Preserved limits and failures

Signed14 completed 62 stored obligations, including one committed Create,
returned-subject opening, cancellation without Enter and ordinary disconnect.
It remains a whole failure: the client stayed alive at the original 60s no-EOF
trigger, was then retired by the existing cleanup, and exited -15; server0,
wrapper1, all four EOF. The one guarded private stack capture returned0, but
sandbox executable/shared-library symbols could not be loaded. Its unresolved
native frames do not establish a close cause or justify a close-policy change.

Signed14's result raster was captured during an ordinary authorization refresh.
The later native returned-action interaction passed, but that image is not visual
acceptance of the committed result. The next separately labelled diagnostic waits
on existing owner notifications for the accepted visible view before its raster.
It retains the original deadlines and does not retry or replay the domain action.

Signed15 then failed that accepted-view check with client1/server0 and all four
EOF. Its raster shows the returned action, but the renewed offer replaced the
completion message with stale-schema advice. ShowOutcome now installs the received
outcome's native label beside its own returned actions. The current form still
shows its distinct draft/schema state and remains locked after submission. The
reply, LastOutcome, exact targets, resolution, submission and authorization paths
are unchanged. No separate outcome store or executor is introduced.

The final16 build completed, but was not launched: review of its new diagnostic
found a reference to the pre-renewal button, which the ordinary form owner may
retire. Final17 reacquires the installed input before checking its disabled state.
This is an unrun diagnostic correction, not a claimed product lifetime defect.

Signed17 verifies the retained completion label and submitted-draft lock after
renewal, but fails later at Cancel: its actual rectangle ends at y887 while the
outer clip ends at y878. The additional result content makes the whole operation
panel taller than the viewport again. An explicit new selection now asks the
same scroll owner to reveal the actual recovery/Cancel row, rather than enclosing
the oversized panel. The form's bounded fields and primary action precede that
row. No padding constant, assertion tolerance, deadline or synthetic scroll was
introduced to hide the nine-pixel failure.

Source-only builds, native Control events and synthetic XR owner samples are
software evidence. They do not prove physical input, readable headset pixels,
comfort, ordinary human navigation or resolution of historical shutdown pauses.

## Design references

The existing GUI contract governs hierarchy, preserved forms/drafts, explicit
placement and the shared palette. Current primary comparisons were read before
implementation: [Android XR visual design](https://developer.android.com/design/ui/xr/guides/visual-design),
[Microsoft buttons](https://learn.microsoft.com/en-us/windows/mixed-reality/design/button)
and [typography](https://learn.microsoft.com/en-us/windows/mixed-reality/design/typography).
Their device-specific numbers are heuristics, not Godot-pixel equivalences or Vive
certification. Current placement, scale, mapping, neutral and authority gates are
unchanged by this slice.
