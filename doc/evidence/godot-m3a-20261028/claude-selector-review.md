## body_frame_pose and view_frame/3

- The schema is consistent across `placed`, `attachment_pose`, `available_parent`, `model_transform`, `scoped_transform`, `mark_body` and `physics_view_body`. Terrain stays excluded by `geometry_binding`, which is right. `physics_scene_frames` dedups one `body_frame` per `(B,R)` and reads the edge transforms inside the signed view, so a frame edit invalidates through the existing read set and the body revision bump.
- **Two chains, two uses.** `ViewChain` must be applied to the whole streamed frame for an interior view; each `body_frame` transform list applies only to its reframed marks and is independent of the view chain. State that in the receipt doc so M3b does not compose both.
- **Gap 1, root-level bodies.** `physics_view_body(body_frame_pose(B,R), ...)` ([quod_physics.pl:721](/home/yan/src/quod_worktrees/pearl-stone/priv/ontologies/quod_physics.pl:721)) and `physics_scene_frames` require a `framed` pose, but bodies installed directly at the root keep a plain pose (`physics_install_component` with `Path = []`). A decorative occurrence of such a body makes the whole view unavailable. Accept an unframed body with `Transforms = []` and `Id = space_occurrence_id([])`.
- **Gap 2, direct display references.** `space_exposed_subjects` (live quod_space.pl:481) only reaches `in_frame/2` through `space_placement` at the displaying space, so a `space_member` display of an entity itself always yields `source_layout` and the entity's container-local transform applied in the wrong frame. Resolve a display subject through its real assignment (`Ns::space_assignment(E,_,Container)`, then that container's domain) so a single-entity display also receives `body_frame_pose` in the same domain and a refusal or explicit static layout otherwise.
