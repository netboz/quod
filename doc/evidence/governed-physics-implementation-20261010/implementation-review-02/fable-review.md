## 1. Capability plan: not ready for local implementation

The plan stays inside the user's rulings. It keeps authority and structure at the world's own ontology as `doc/world.md` lines 173 to 176 require, adds no compatibility branch, and does not revive the mutable-module experiment. It is still a statement of intent. The following mechanics are missing before anyone can write code.

- **High. Activation height and loader site are undefined.** The only module loader is `prepare_genesis_modules` at `tree/src/quod_committed_projection.erl:144-160`. It fires solely for the single genesis transaction at index 1 with applied 0, reading the manifest from the genesis entry. The plan must state that the effective registry at height H is a deterministic function of the committed ledger, that the activation entry loads its profile after its own validation, and that live apply and cold replay use the same path. Without that, a validator that applied the activation live keeps the old registry while a restarted node replays with the new one. Any later entry whose policy consults a bridge then diverges silently, because `new_est` sets the unknown-predicate flag to fail at `quod_committed_projection.erl:58-59`.
- **High. "Cannot be hot swapped" contradicts determinism.** Live validators apply every entry in a running engine. Either the activation loads in-process at its index on every node, with the cold release needed only where the module code is absent, or the plan needs a quiescence primitive that refuses ordinary commits in that scope until restart. No such primitive exists. Pick the first and say so. Before that, check whether `erlog_int:add_compiled_proc` on the shared MVCC ref at `quod_predicates.erl:312` is snapshot-isolated. If not, proofs borrowed at height H can observe a registry from H+1. I could not verify this from the frozen tree.
- **High. Reserved record and both validation seams are unnamed.** A new functor must join `reserved_clause_head` at `quod_ontology.erl:851-854`, and both refusals at `quod_commit_validation.erl:316-319` and `739-741` must gain an authenticated exception. Today both refuse unconditionally. The plan says "extend" without naming the predicate or the exception rule.
- **High. Target validators cannot see root's receipt.** A target only materializes its own plan, see `maps:find(Target, Plans)` at `quod_commit_validation.erl:600-602`, and `validate_prepared_material` receives only its own diff, read check and transcript. The plan must specify what the target checks: that the group manifest names the pinned root identity as participant, that the target record carries the group reference so the receipt is auditable in root's ledger, and an OCC read check on the previous epoch fact. Root's own validators enforce the receipt's domain policy. Atomicity does the rest.
- **Medium. The acting principal and call path into root are unnamed.** Root mutations need an admitted node or a root administrator, with a direct chain of `[]`, `[Namespace]` or the agent's own origin, see `quod_root.pl:24-29` and `44-46`. An atomic transaction originating in the lobby with a human principal from the user ontology cannot enter root. The activation must start from the release authority's node principal or from the administrator's own ontology.
- **Medium. Root has no released-profile catalogue.** Catalogue rows deliberately carry no module names, `quod_root.pl:147-157`. The plan needs a named root fact for the ordered module list and digest, who writes it, and whether validators read it through a public goal.
- **Medium. Digest enforcement would create a second semantics.** The existing contract is presence enforced, digest as provenance only, see `quod_predicates.erl:157-177` and the comment at `195-202`. The plan's "registry/code digest and participating validator profile" implies strict matching. Decide, and prefer the genesis rule. Also note that a follower replaying this ledger through `quod_foreign_log` hits the same loader, so "participating validators" must include every follower node.
- **Medium. Fence binding and revocation have no concrete site.** The physics fence is world, authority, epoch, generation plus incarnation and structure at `quod_physics.erl:599` and `303`, mirrored at `quod_physics_predicates.erl:86-87`. Either the profile-epoch fact must be read inside `physics_projection/2` so the resource basis captures it, or it joins the fence tuple. Define what a revoked profile does to an installed world. Requiring the profile fact in the space-enabled rule is the simplest answer.
