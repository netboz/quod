Consultative Fable review, 2026-10-06. This is not an approval. Parent must verify all claims, particularly the proposed expiry-based inference of non-admission.

**Verdict.** The design in the tracker is sound in intent, but one verified fact changes its shape: a node that is not a root validator cannot author or execute any root or quod:node lifecycle action today. Enrollment "independent of root committee" therefore cannot be "the new node submits the create and executes it locally". The parent's proposed composition (signup-style transaction with a durable custodian hosting delegation, then an ordinary pinned join, then a node-owned self-hosting and membership transition, with no new remote executor and no authority bypass) is consistent with every finding below.

## Enrollment: executor, placement, custody

- **Verified blocker: non-members cannot author root transactions.** The consensus ingress accepts a transaction only when its author is a current validator ([quod_simplex.erl:12404](/home/yan/src/quod/src/quod_simplex.erl:12404), applied to local authors at [quod_simplex.erl:8420](/home/yan/src/quod/src/quod_simplex.erl:8420)), so a non-member cannot even relay a native root append. The signed-goal ingress independently refuses local execution on an observer and forwards to a validator ([quod_client_goal_target.erl:69](/home/yan/src/quod/src/quod_client_goal_target.erl:69)). For a non-admitted node, the root proof always runs on a remote validator.
- **Verified: the executor is the transaction author, so the ledger is born on the remote validator.** The effect binds the proof session's signer as executor ([quod_ontology_predicates.erl:150](/home/yan/src/quod/src/predicates/quod_ontology_predicates.erl:150)) and validation requires executor to equal the author ([quod_effect.erl:103](/home/yan/src/quod/src/quod_effect.erl:103)). The tracker's "do not assume root-side creation executes on the new node" is confirmed: it never does for a non-member.
- **Verified: an ontology created on a remote executor is ephemeral and unreachable.** The manager treats creation as admission only; restart authority is root bootstrap, catalogue, or the executor's own hosting facts ([quod_namespace_manager.erl:981](/home/yan/src/quod/src/quod_namespace_manager.erl:981)). Advertisement needs a node row backed by a committed `hosts_ontology` fact ([quod_namespace_manager.erl:1419](/home/yan/src/quod/src/quod_namespace_manager.erl:1419)). The executor has neither for a stranger's identity ontology, so the new node could never find a route to join it. The same hazard exists for signup when the executor is not `signup_host`; I did not verify that live.
- **Verified: joining has the same wall.** `join_ontology` is a quod:node action whose effect executes on the author ([quod_node.pl:40](/home/yan/src/quod/priv/ontologies/quod_node.pl:40)), and the new node is at best an observer of quod:node. It cannot run that effect either. The applicant's local copy must come through the manager's fact-driven pinned join, not through a join action it authors.
- **Suggested composition (minimal, no new engine).** Mirror signup exactly, with the host chosen by policy, not by the applicant:
  1. quod:node gains a signup-style applicant principal: `instance_of(agent, enrolling(Key))` and `agent_key(enrolling(Key), Key, active)` as rules gated by an enrollment policy fact, like [quod_signup.pl:9](/home/yan/src/quod/priv/ontologies/quod_signup.pl:9). This lets a key-only node sign an ordinary goal before it has an identity.
  2. Root delegates via `ontology_creation_policy(quod:node, Anchor)`; quod:node's `ontology_creation_allowed/3` derives the full recipe from the key (deterministic namespace from the key, like `signup_name`, plus the exact node_execution source and terms). Erlang's `creation_terms` ([quod_node_actor.erl:282](/home/yan/src/quod/src/quod_node_actor.erl:282)) then becomes Prolog policy or is called from it. Root's third `can_create_ontology` clause already supports this ([quod_root.pl:145](/home/yan/src/quod/priv/ontologies/quod_root.pl:145)).
  3. The enrollment goal composes, in one atomic transaction, `quod:root::create_ontology(...)` with `HostNs::request_ontology_hosting(Applicant, HostNode, Name, Anchor, discoverable)` on the executing validator's own node ontology, as [quod_signup.pl:61](/home/yan/src/quod/priv/ontologies/quod_signup.pl:61) does. The executing validator must be the host, so policy needs "the host is the node executing this proof". There is no Prolog predicate for that today: `me/1` returns the principal outside reaction context ([quod_runtime_predicates.erl:49](/home/yan/src/quod/src/predicates/quod_runtime_predicates.erl:49)). This is the one concrete missing capability I found. A read-only bridge exposing the executing node's verified reference is small and does not add an executor.
  4. The new node then joins its own identity ontology through the existing pinned-join path ([quod_ontology.erl](/home/yan/src/quod/src/quod_ontology.erl) `prepare_host_join`) under the manager's node-actor bootstrap, with the custodian's hosting row making the ontology routable. Once its local copy is ready and the pointer is verified ([quod_node_actor.erl:255](/home/yan/src/quod/src/quod_node_actor.erl:255)), the node commits its own self-hosting row and the membership transition in its own ontology. An alternative is seeding the identity ontology's committee with the applicant key at genesis; `peer_admitted` is reserved from initial terms (`reserved_clause_head` in [quod_ontology.erl](/home/yan/src/quod/src/quod_ontology.erl)), so that would need a reviewed exception for the enrollment recipe only. The parent's chosen order avoids that exception.
- **Verified: there is no production enrollment seam at all.** `bind/4` and `creation_options/4` are called only from tests. The founder's live identity was provisioned by hand. Startup initiation must be added; the natural trigger is the root `replay_ready` or `proof_ready` edge the manager already subscribes to, gated on "pointer absent".
- **Custody: what already exists.** Once a proof stages the effect, the effect journal is crash-durable from `transaction_bound` onward and resolves by the exact transaction outcome, never re-proving ([quod_effect_journal.erl:1265](/home/yan/src/quod/src/quod_effect_journal.erl:1265)). The idempotency key is the desired state ([quod_effect_journal.erl:1009](/home/yan/src/quod/src/quod_effect_journal.erl:1009)), and a second create for the same name on the same executor resumes the existing ledger rather than minting a new anchor ([quod_ontology.erl:485](/home/yan/src/quod/src/quod_ontology.erl:485)). The executor side is covered.
- **Custody gap: the applicant's pending signed request has no owner.** Between "signed request built" and "pointer stored", nothing durable names the operation on the new node. Crash before send is safe only if nothing was sent. Uncertain send (forwarded, reply lost) is the dangerous case: on restart the node sees no pointer and would build a fresh operation id, and a second committed creation on a different executor yields a second anchor (archived plan 7.1 explicitly tolerates duplicate names). Suggestion: extend the existing pointer file, not add a store. `node.actor` already has one owner with atomic write and fail-closed replacement ([quod_identity.erl:133](/home/yan/src/quod/src/quod_identity.erl:133)). Add a pending form holding the exact signed bytes and signature, written before submission. On restart with a pending form: resolve by `quod_client_goal_ingress:resolve_operation/2` ([quod_client_goal_ingress.erl:105](/home/yan/src/quod/src/quod_client_goal_ingress.erl:105)). Committed means bind from the outcome's target anchor. Rejected or expired-and-not-found means a new request is safe. Pending or unavailable means wait on the existing readiness notices until the signed expiry, never resubmit. This matches the exact-operation rule already applied to agents (`invoke_live` resolve branch in [quod_agent.erl](/home/yan/src/quod/src/quod_agent.erl)).
- **Pending expiry answer (the parent's critical question).** Strict no-resubmission and automatic progress are compatible, because a signed request carries an absolute expiry and the proof deadline is capped by it ([quod_prolog.erl:1826](/home/yan/src/quod/src/quod_prolog.erl:1826)). Ordered apply does not re-check the wall clock, so the terminal boundary is expiry plus proof timeout plus clock skew. Rules:
  - Before that boundary with no claim: resolve-only, wait on the existing readiness notices. This is the only window where crash-before-send and uncertain send are indistinguishable, and it is bounded by the expiry the applicant chose.
  - After that boundary with no claim: the operation can never be admitted. Retiring the pending form and building a new operation is not an uncertain-write resubmission. It is the effect journal's own "not found with neither custody nor continuous admission, retire visibly" rule applied on the applicant side. A short enrollment expiry keeps the strand window small.
  - The pending pointer form must store the signed bytes, so expiry and operation id survive restart.
  - A second layer removes the need to distinguish the two cases at all. Mirror the signup receipt ([quod_signup.pl:67](/home/yan/src/quod/priv/ontologies/quod_signup.pl:67)): the enrollment rule requires no existing receipt for the key and asserts one in the same transaction. Two admitted operations for one key then cannot both create an identity; the second fails under quod:node consensus through the ordinary read-set conflict. A restarted applicant reads the receipt by key, binds if present, and otherwise applies the expiry rule above. The receipt is consumed by an acknowledge after the pointer is stored, as signup does, so quod:node keeps no permanent per-node table. The transaction becomes atomic across root, quod:node and the custodian's node ontology, which is the ordinary atomic lane signup already uses.
- **Bind step note.** `bind/4` stores the pointer then casts `adopt_node_actor`; a crash between the two is harmless because init reloads the pointer ([quod_namespace_manager.erl:752](/home/yan/src/quod/src/quod_namespace_manager.erl:752)). A crash before the pointer write is the pending-form case above.
- **Self-hosting row.** The identity ontology is not advertised by its owner unless its own ontology holds `hosts_ontology(Self, Ns, Anchor, discoverable)`, and genesis terms cannot name the anchor. In tests this row is committed after binding. The receiver fetches the author's ontology from the advertiser's endpoint directly ([quod_directory_control.erl:1420](/home/yan/src/quod/src/quod_directory_control.erl:1420) onward), so validation does not need the row, but `knows_ontology_host` resolution does. Either a node-actor author may always carry its own identity row and the receiver accepts that one row by identity equality, or the post-bind self-host transaction must itself be recoverable. The parent's node-owned transition step covers the second form.

## Advertisement

- **Verified root cause of `advertisement_author_unavailable`.** Every node has root as a `bootstrap` row ([quod_namespace_manager.erl:160](/home/yan/src/quod/src/quod_namespace_manager.erl:160), [quod_namespace_manager.erl:1419](/home/yan/src/quod/src/quod_namespace_manager.erl:1419)). The publisher partitions bootstrap and system rows to the root author, which exists only for current control peers ([quod_directory_control.erl:1217](/home/yan/src/quod/src/quod_directory_control.erl:1217)). A nonempty partition with no author rejects the whole publication ([quod_directory_control.erl:1252](/home/yan/src/quod/src/quod_directory_control.erl:1252)). Moving system rows to the node author is not enough: the root row alone still trips it. A node whose admission is later revoked hits the same failure.
- **Receiver side must change in step.** A node-actor generation containing any non-node row is rejected ([quod_directory_generation.erl:147](/home/yan/src/quod/src/quod_directory_generation.erl:147)). System rows are already checked against the receiver's own catalogue regardless of author ([quod_directory_generation.erl:170](/home/yan/src/quod/src/quod_directory_generation.erl:170)), so allowing `system` under a node-actor author needs only the author branch relaxed. The rule set the parent started is coherent: root row only with the pinned network anchor, system rows from any verified node actor against the catalogue, node rows against `hosts_ontology` facts, private rows never.
- **Sender side.** Partition into root-only versus system-plus-node. When the root author is unavailable and holds no rows, the unavailable-author branch must yield `none` rather than the error ([quod_directory_control.erl:1251](/home/yan/src/quod/src/quod_directory_control.erl:1251)). The "cannot withdraw" rationale behind the current error does not apply: a never-authored row has nothing to withdraw, and a revoked key's old generation expires by lease.
- **Cautions on the started edits.** Keep refusing `bootstrap` rows whose anchor is not the network identity. The projection check reads only bodyless facts ([quod_directory_generation.erl:183](/home/yan/src/quod/src/quod_directory_generation.erl:183)), so any rule-derived key or hosting fact is invisible to receivers. The `{node_actor, node}` installed notice is the right publication trigger; subscribe before snapshot.
- **Revocation and withdrawal.** Control-peer changes retire links immediately ([quod_directory_control.erl:554](/home/yan/src/quod/src/quod_directory_control.erl:554)) and later root-bootstrap generations from the revoked key are refused at ingest ([quod_directory_control.erl:1318](/home/yan/src/quod/src/quod_directory_control.erl:1318)). Already-installed rows are not purged; they expire by lease. Node-key revocation works the same way: validation requires a bodyless active `agent_key` fact ([quod_directory_generation.erl:114](/home/yan/src/quod/src/quod_directory_generation.erl:114)).
- **Transition bootstrap to enrolled.** Per-author generation ordering handles it: the root author republishes with fewer rows and supersedes itself. Nothing else is needed.
- **Atomic rejection risk.** A receiver whose root lags the catalogue rejects an entire generation, including valid node rows, as `unauthorized_generation`, terminally for that generation. Existing behavior, but it becomes more visible once every node carries system rows. Worth a retry-on-catalogue-change rather than a terminal verdict.
- **Self-certification caveat.** A node identity ontology is validated by the key that owns it, from a single-member committee. Advertisement therefore proves only "this key says it hosts X". Target role and ACL checks at use remain the authority, as the archived plan states. Open enrollment therefore lets any key publish hints network-wide, but grants no committee seat and no foreign ACL.
