# Full startup barrier review correction

This supersedes the earlier recommendation to remove the full-application startup notification. Both the authentication and router readiness notifications subsequently received their own scoped implementation.

Checking the one claim that matters here: what the ingress does when the router process does not exist yet.

The reasoning holds, with one sharpening.

- **Router absent is pre-send, verified.** The router's `call/1` returns `{error, pre_send}` when `whereis` finds no process ([quod_client_goal_router.erl:101](/home/yan/src/quod/src/quod_client_goal_router.erl:101)), and the ingress treats `pre_send` as try-next-route, ending in `signed_target_unavailable` when every route is exhausted ([quod_client_goal_ingress.erl:409](/home/yan/src/quod/src/quod_client_goal_ingress.erl:409)). That is in the allowlist, so an early auth notice during boot yields a recorded definite refusal, never an unresolved row. The uncertain mapping is reserved for `{error, unavailable}`, which only a live router produces after it accepted the call ([quod_client_goal_router.erl:123](/home/yan/src/quod/src/quod_client_goal_router.erl:123)), and for the monitored-call timeout. Boot ordering cannot reach it.
- **Why the notice alone is not enough.** After that early refusal the manager parks on `enrollment_route` for `{quod:node, Anchor}` and calls `route_needed`. If the route was already known before the router started, no `directory_route_available` edge follows, and nothing else in the manager's wake set names "the router now exists". The remaining edges (root or quod:node replay and proof readiness, policy applied-live, topology) do fire on a normal boot and would usually cover it, but relying on them makes recovery of a refused first dispatch depend on unrelated traffic. So a distinct full-supervisor barrier is justified.
- **The restored app cast is the right barrier.** Placing it after `maybe_start_directory_tracking` means every supervisor child, including cursor, router and vault, is up and tracking has started. It is one cast into the same coalesced job with the dirty flag, so with the auth notice it is at most one extra `enroll/0` run, no new path or process. The two triggers have distinct meanings: the notice covers an auth-only restart, the cast covers the whole-tree boot. Both are owner-driven, neither is a timer.
- **One residual, consultative.** The same "already known route, no new edge" gap exists for any refusal recorded while the router is down after boot, for example a router-only supervisor restart. A `client_goal_router` readiness notice of the same shape would close it symmetrically, but router crashes are rare and the next readiness edge of any kind re-runs the job, so this is not a blocker for this tree.

The stop marker after the current gate and a whole clean boundary re-covering the one-line restoration is the correct handling. Nothing here touches refusal or recovery authority.
